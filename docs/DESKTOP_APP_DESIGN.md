# PandaWiki 桌面端详细设计

## 1. 设计目标

本设计用于指导 PandaWiki 桌面端的首期实现。桌面端不是管理后台的桌面化封装，而是一个面向知识工作者的轻量桌面编辑器。

首期目标：

1. 连接 PandaWiki 服务端
2. 浏览并打开文档
3. 编辑富文本文档
4. 编辑与预览 Markdown 文档
5. 使用 AI 问答

首期不做：

- 后台设置
- 权限与成员管理
- 版本发布管理
- 多人协同编辑
- 大文档块状协同
- 全量离线能力

一句话定义产品形态：

> 一个可以连接 PandaWiki、支持富文本与 Markdown 编辑、并具备问答能力的桌面知识编辑器。

---

## 2. 设计原则

桌面端遵循以下原则：

### 2.1 保留 Web 端主站地位

- `web/admin` 继续是管理后台主入口
- `web/app` 继续是用户访问主入口
- 桌面端只承担编辑与问答，不替代整个 Web 产品

### 2.2 复用能力，不复用整页

优先复用：

- 接口模型
- 文档渲染规则
- 编辑器扩展能力
- 问答业务链路

避免复用：

- `web/admin` 的整页布局
- `web/admin` 的路由树
- 后台专属状态管理

### 2.3 首期优先稳定

桌面端第一阶段默认：

- 单人编辑
- 远程保存
- 不引入协同编辑

原因：

- 当前协同编辑在 Web 端本身就是复杂模块
- 桌面端首期目标是先把“可稳定编辑、可稳定保存、可稳定问答”做出来

### 2.4 安全边界明确

- Node 文件系统能力只能暴露给 Electron 主进程
- 渲染进程通过 `preload + contextBridge` 调 IPC
- 不允许渲染层直接使用不受控的 Node API

## 3. 产品边界

## 3.1 用户场景

桌面端主要覆盖三类场景：

### 场景 A：打开知识库文档进行编辑

用户登录 PandaWiki 桌面端，进入知识库文档，编辑富文本或 Markdown 内容，并保存回服务端。

### 场景 B：阅读文档并进行问答

用户打开某篇文档，边阅读边向 AI 提问，获取针对文档内容的问答结果。

### 场景 C：本地 Markdown 写作

用户打开本地 Markdown 文件，进行编辑和预览，获得类似 Typora 的体验。

## 3.2 首期能力矩阵

| 能力 | 首期是否支持 | 说明 |
|------|--------------|------|
| 远程登录 | 支持 | 连接 PandaWiki 服务 |
| 文档列表/树浏览 | 支持 | 浏览知识库结构 |
| 富文本查看 | 支持 | 打开服务端富文本内容 |
| 富文本编辑 | 支持 | 单人编辑 |
| Markdown 查看 | 支持 | 服务端/本地均支持 |
| Markdown 编辑 | 支持 | 单人编辑 |
| Markdown 预览 | 支持 | 必须支持 |
| AI 问答 | 支持 | 基于现有后端接口 |
| 本地文件打开/保存 | 支持 | 仅 Markdown 首期必做 |
| 本地富文本文件 | 暂不支持 | 首期不做复杂本地富文本格式互转 |
| 协同编辑 | 不支持 | 首期明确关闭 |
| 离线编辑同步 | 不支持 | 后续增强 |
| 自动更新 | 可选 | 第二阶段再接入 |

## 5. 进程边界设计

## 5.1 主进程职责

主进程只处理桌面能力，不承载业务页面逻辑。

建议职责：

1. 创建窗口
2. 管理应用菜单
3. 注册快捷键
4. 处理文件打开/保存对话框
5. 读写本地文件
6. 存储本地配置
7. 管理最近文件列表
8. 处理协议唤起或文件双击打开

不建议主进程承担：

- 直接发业务接口请求
- 文档内容解析
- 问答流式渲染
- 编辑器状态管理

## 5.2 Preload 职责

`preload.ts` 负责暴露受控桌面能力。

建议向渲染层暴露：

- `desktop.file.open()`
- `desktop.file.save()`
- `desktop.file.saveAs()`
- `desktop.file.readRecent()`
- `desktop.config.get()`
- `desktop.config.set()`
- `desktop.window.onMenuAction()`

原则：

- IPC 通道名固定
- 参数结构显式定义
- 不直接透传 Node 原生对象

## 5.3 渲染进程职责

渲染进程负责全部业务页面与交互。

包括：

- 登录状态
- 文档加载
- 编辑器状态
- Markdown 编辑与预览
- AI 问答流式输出
- 保存状态提示
- 本地文件与远程文档的页面切换

## 6. 页面与路由设计

## 6.1 页面清单

首期建议只保留以下页面：

| 页面 | 作用 |
|------|------|
| 登录页 | 登录 PandaWiki 服务 |
| 工作区页 | 展示知识库、最近文档、本地文件入口 |
| 富文本编辑页 | 查看/编辑富文本文档 |
| Markdown 编辑页 | 编辑/预览 Markdown |
| 问答页 | 独立问答或文档侧边问答 |

## 6.2 路由建议

```text
/login
/workspace
/editor/rich/:nodeId
/editor/markdown/:nodeId
/editor/local-markdown
/chat
```

补充说明：

- 本地 Markdown 可不带 `nodeId`
- 问答页既可以独立路由，也可以嵌入编辑页右侧抽屉
- 如果首期想更像 Typora，可以让 Markdown 编辑页成为核心入口

## 6.3 界面布局建议

推荐桌面端采用三栏或双栏布局：

### 方案 A：双栏布局

- 左栏：知识库/文件导航
- 右栏：编辑区

适合首期 MVP。

### 方案 B：三栏布局

- 左栏：知识库/文件导航
- 中栏：编辑区
- 右栏：问答/文档信息

更适合长期形态。

推荐结论：

- **首期先双栏**
- 问答作为侧边抽屉或右侧可折叠面板

## 7. 编辑器方案设计

## 7.1 富文本编辑器

推荐直接基于现有 `web/admin` 的编辑器能力抽一层 `editor-core`。

复用来源：

- `web/admin` 的 Tiptap 扩展集合
- 工具栏动作定义
- 内容保存格式
- 富文本只读/编辑模式切换

但需要做两件事：

1. 去掉协同编辑相关依赖
2. 把与后台页面强耦合的逻辑拆出来

桌面端首期富文本编辑器应具备：

- 标题、段落、列表
- 加粗、斜体、删除线、引用
- 图片插入
- 代码块
- 表格
- 链接
- 撤销/重做

不建议首期纳入：

- 协同编辑
- 评论批注
- 大文档分块机制

## 7.2 Markdown 编辑器

首期建议采用“编辑区 + 预览区”分离结构。

推荐方案：

- 左侧纯文本编辑区
- 右侧 Markdown 预览区
- 支持编辑/预览/分栏三种模式

编辑器内核建议分两阶段：

### 阶段 1

- 使用 `textarea` 或轻量编辑封装
- 复用 `web/app` 的 Markdown 渲染规则
- 先把打开、编辑、预览、保存链路做稳

### 阶段 2

- 引入 CodeMirror 6
- 增强语法高亮、折叠、快捷补全、目录定位

为什么不建议一开始就重型投入 Markdown 编辑器：

- 你的当前目标是“能替代 Typora 的核心能力”
- 真正第一优先是稳定和可维护，不是一次做完所有高级编辑体验

## 7.3 Markdown 渲染复用

建议优先复用 `web/app` 的这些资产：

- Markdown 渲染规则
- `remark-gfm`
- `remark-math`
- `rehype-katex`
- `rehype-raw`
- `rehype-sanitize`
- 代码高亮
- Mermaid / KaTeX 的显示策略
- `markdown.css`

这样可以保证：

- Web 端和桌面端的 Markdown 视觉结果尽量一致
- 后续 Bug 修复可以共享

## 7.4 文档数据格式

桌面端需要支持两类文档：

### 远程文档

来源：PandaWiki 服务端节点。

字段至少包括：

- `nodeId`
- `kbId`
- `title`
- `content`
- `contentType`
- `updatedAt`

### 本地文档

来源：本地文件系统。

字段至少包括：

- `filePath`
- `title`
- `content`
- `contentType = md`
- `dirty`
- `lastSavedAt`

建议在桌面端定义统一视图模型：

```ts
type DesktopDocument = {
  source: 'remote' | 'local';
  id: string;
  title: string;
  content: string;
  contentType: 'md' | 'html' | 'rich';
  dirty: boolean;
  updatedAt?: string;
  filePath?: string;
  nodeId?: string;
  kbId?: string;
};
```

这样页面层就不用区分太多分支。

## 8. AI 问答设计

## 8.1 能力来源

桌面端问答优先复用 `web/app` 现有链路。

重点复用：

- 请求协议
- 会话模型
- SSE / 流式消息处理
- 错误提示与重试逻辑

## 8.2 问答交互形态

建议支持两种形态：

### 形态 A：独立问答页

适合泛知识库问答。

### 形态 B：文档侧边问答

用户在编辑或阅读某篇文档时，右侧直接提问。

推荐首期优先：

- 编辑页内嵌右侧问答面板

原因：

- 更符合“边看边问”的桌面使用场景
- 对替代 Typora 更有差异化价值

## 8.3 问答上下文

建议首期支持两类上下文：

1. 当前文档上下文
2. 整个知识库上下文

用户可切换：

- “仅针对当前文档提问”
- “针对整个知识库提问”

这样问答体验会明显更清晰。

## 9. 数据流设计

## 9.1 登录流程

```text
用户输入服务地址 + 账号密码
  -> 渲染层发起登录请求
  -> 获取 token / 用户信息
  -> token 写入本地安全存储
  -> 进入工作区
```

建议：

- 服务地址可配置
- 支持切换多个 PandaWiki 实例

## 9.2 远程文档打开流程

```text
工作区点击文档
  -> 拉取文档详情
  -> 判断 contentType
  -> 跳转富文本页或 Markdown 页
  -> 初始化编辑器
  -> 用户编辑
  -> 保存回服务端
```

## 9.3 本地 Markdown 打开流程

```text
菜单/按钮触发“打开文件”
  -> 主进程弹出文件选择框
  -> 主进程读取文件内容
  -> preload 返回给渲染层
  -> 渲染层创建本地文档模型
  -> 进入本地 Markdown 编辑页
```

## 9.4 保存流程

### 远程保存

```text
用户触发保存
  -> 调用远程保存接口
  -> 更新页面 dirty 状态
  -> 提示保存结果
```

### 本地保存

```text
用户触发保存
  -> 如果已有 filePath，直接通过 IPC 写文件
  -> 如果无 filePath，触发 Save As
  -> 更新 dirty 状态
```

## 10. 状态管理设计

## 10.1 建议拆分

桌面端建议至少拆分为以下状态域：

1. `authStore`
2. `workspaceStore`
3. `documentStore`
4. `editorStore`
5. `chatStore`
6. `settingsStore`

## 10.2 关键状态

### `authStore`

- 当前服务地址
- token
- 当前用户
- 登录状态

### `workspaceStore`

- 当前知识库
- 文档树
- 最近文档
- 最近本地文件

### `documentStore`

- 当前文档元数据
- 文档来源（本地/远程）
- 保存状态
- 是否脏数据

### `chatStore`

- 当前会话
- 消息列表
- 流式输出状态
- 关联文档上下文

## 11. 与现有项目的复用关系

## 11.1 可直接复用

优先直接复用：

- `web/app` 的 Markdown 渲染依赖和样式
- `web/app` 的问答接口协议
- `web/admin` 的富文本编辑器扩展能力
- `web/packages/icons`
- `web/packages/themes`

## 11.2 建议抽离后复用

需要先抽层再复用：

- `web/admin` 的编辑器工具栏逻辑
- `web/admin` 的文档详情请求与保存模型
- `web/app` 的问答消息处理逻辑
- `web/app` 的文档内容渲染封装

## 11.3 不建议复用

不建议直接拿来复用：

- `web/admin` 的整套路由与布局
- `web/admin` 的协同编辑代码
- `web/app` 的 Next.js 页面壳
- 依赖浏览器 SSR 语义的页面逻辑

## 12. 本地能力设计

## 12.1 本地配置

建议存储：

- 最近连接的服务地址
- 最近打开的远程文档
- 最近打开的本地文件
- 窗口状态
- 编辑器偏好设置

建议使用：

- `electron-store` 或同类轻量存储

## 12.2 本地文件支持范围

首期只建议支持：

- `.md`
- `.markdown`
- `.txt`（可选，以 Markdown 方式打开）

首期不建议支持：

- `.docx`
- `.pdf`
- 本地富文本专有格式

原因：

- 一旦扩展到 Office/PDF 互转，复杂度会明显上升
- 当前桌面端目标仍然是替代 Typora，而不是替代 Office

## 12.3 自动保存

建议首期支持轻量自动保存：

- 本地 Markdown：可定时自动保存
- 远程文档：先只保留手动保存

原因：

- 远程自动保存会牵扯更复杂的冲突与提示机制
- 本地自动保存风险更可控

## 13. 安全设计

## 13.1 Electron 安全基线

建议默认开启：

- `contextIsolation: true`
- `nodeIntegration: false`
- `sandbox: true`（若兼容性允许）

并要求：

- 所有桌面能力通过 preload 暴露
- 所有外部 URL 打开走系统浏览器
- 不在渲染层执行不受控脚本

## 13.2 Token 存储

首期可接受方案：

- 存本地安全配置中

更优方案：

- 后续接入系统 Keychain / Credential Store

建议结论：

- MVP 先落本地存储
- 第二阶段再接系统级凭证保存

## 16. 风险点

## 16.1 富文本能力拆分风险

风险：

- `web/admin` 的编辑器代码可能和页面状态有较强耦合

建议：

- 先最小化抽取编辑器扩展层
- 不要一开始试图完整搬迁所有工具栏能力

## 16.2 Markdown 编辑器体验预期风险

风险：

- 如果首期只用轻量编辑区，体验可能弱于 Typora

建议：

- 首期保证稳定
- 第二阶段引入 CodeMirror 6 补体验

## 16.3 问答接口适配风险

风险：

- `web/app` 的问答链路可能和页面上下文强耦合

建议：

- 先抽 `chat-core`
- 把消息模型、SSE 解析和错误处理独立出来

## 16.4 本地与远程双模型风险

风险：

- 同一个页面既支持本地文档又支持远程文档，状态分支容易变复杂

建议：

- 提前定义统一 `DesktopDocument` 视图模型
- 页面层只依赖统一模型

## 17. 推荐的下一步工程动作

如果按这个设计继续推进，推荐下一步按下面顺序执行：

1. 在 `web/pnpm-workspace.yaml` 中预留 `desktop` 和后续 `packages/*` 扩展空间
2. 初始化 `web/desktop`
3. 先抽 `doc-core` 和 `chat-core`
4. 再做桌面端登录、工作区、Markdown 编辑
5. 最后接富文本编辑器

原因：

- Markdown 编辑链路更直、更适合作为桌面 MVP 起点
- 富文本编辑器拆分难度更高，放在后面更稳

---

## 18. 最终建议

桌面端最合理的首期实现方式是：

- **独立 Electron 应用**
- **远程 PandaWiki 编辑为主，本地 Markdown 为辅**
- **先做 Markdown 与问答，再做富文本增强**
- **明确关闭协同编辑和复杂后台能力**

这样做的结果是：

- 目标清晰
- 研发成本可控
- 与现有仓库兼容
- 能较快交付一个真正可用的桌面版本
