## 确认的瓶颈

通过仅记录参数、用量和字节数的临时本地转发，确认兼容接口收到了关闭推理的原生参数，但实际仍返回推理token。有一轮6000输出token全部用于推理，正文为空，等待约97秒后才进入修正。另一次修正的2718输出token中2599为推理。

服务以`reasoning`字段返回推理内容，现用SDK只映射`reasoning_content`，因此原诊断中的`reasoning_characters=0`不能证明没有推理。观察过程没有打印或保存推理正文、凭据或原始请求。

本轮增加兼容网关的统一`reasoning.enabled=false`控制，并保留明确参数不兼容时的一次回退；当前网关仍可能产生推理。不能把提示、参数发送成功或隐藏推理文本等同于推理计算已经关闭。参考[网关推理控制说明](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens)。

## 实现

1. **缩小编辑上下文。** 精简、润色等只根据选中成品内容编辑，不再把整份产品清单重复交给模型。样例输入由约2190 token降至484 token。新增资料、联网、补充事实或核对要求仍走资料读取；保留原有资料选择器但全部属于原成品来源时可采用局部路径。
2. **保留来源安全检查。** 即使不把原文送入模型，仍检查所有依赖来源的权限及固定发布版本哈希。没有通过“减少资料”放宽原访问范围。
3. **明确操作直接执行。** `第三页标题改为“设备巡检”`、`第三页删除第2条`直接修改指定内容块并渲染新版本。原版本、其他页面、未删除要点保持原样。否定、条件、复合和歧义指令继续交由原流程或提示明确范围，不能误执行。
4. **紧凑规划。** 使用本轮短来源编号，服务端恢复真实来源和版本ID后执行原校验；未知编号仍拒绝。计划说明保持简短，正文和实际来源数据不截断、不改写。
5. **兼容已保存进度。** 无新约束的原任务保持旧输入指纹；有约束的旧检查点仅在重新校验后接续。已有局部成果的旧修订保留原提示模式，避免发版后因优化而重做已完成内容。

## 验证

- 助手回归在只复制表结构的专用测试库执行，事务回滚。
- Office流水线没有配置模型仍完成改标题、删除要点、版本发布与原文件保留，验证快捷路径不依赖模型。使用内存私有对象存储、测试预览；上述秒级数字另外用真实本地PDF转换测量。
- 覆盖新增资料不被忽略、无效来源短编号拒绝、越界要点/过长标题拒绝、复合/否定命令不走快捷路径、原稿不变和旧检查点继续处理。
- API和助手Worker入口编译检查；本轮没有修改前端或数据库迁移。
- 业务数据基线为9个栏目、180个节点、16名用户；原Postgres卷为`pandawiki_panda_wiki_postgres`，Compose项目为`pandawiki`。没有启动索引Consumer或更改数据卷。
