# PandaWiki 多端扩展设计

## 1. 背景与目标

PandaWiki 当前已经具备两套 Web 端：

- `web/admin`：管理后台，负责知识库管理、文档编辑、配置和发布
- `web/app`：用户端，负责文档浏览、搜索、问答

本次扩展的目标不是把所有能力完整复制到所有终端，而是按终端场景拆分能力，形成一套可长期维护的多端方案。

当前目标定义如下：

| 终端 | 是否保留/新增 | 核心能力 |
|------|---------------|----------|
| Web 管理端 | 保留 | 现有全套后台能力 |
| Web 用户端 | 保留 | 现有文档浏览、搜索、问答能力 |
| 桌面端 | 新增 | 问答、富文本编辑/查看、Markdown 编辑/查看 |
| App 端 | 新增 | 文档查阅、问答 |
| 小程序端 | 新增 | 文档查阅、问答 |

约束条件：

- `web/admin` 和 `web/app` 必须继续保留
- 桌面端不追求后台管理能力，不承担知识库设置、发布流程、统计等功能
- App 和小程序端只做轻量访问，不承担复杂编辑
- 方案优先考虑代码复用、后续维护成本和稳定性

---

## 2. 结论先行

推荐采用下面这条路线：

1. **Web 保持现状**  
   继续保留 `web/admin` 和 `web/app`，作为主业务入口和能力母体。

2. **桌面端单独做 Electron 应用**  
   不直接把整个 `web/admin` 套进去，而是做一个更轻的“桌面知识编辑器”。

3. **移动端与小程序统一走 Taro 路线**  
   新建一个跨端项目，同时产出：
   - 微信小程序
   - H5 移动端
   后续如需要原生 App，再基于 H5 封装或再引入 React Native / Capacitor。

4. **先抽共享能力，再落终端**  
   在前端 monorepo 里逐步抽出：
   - API Client
   - 文档渲染核心
   - Chat / QA 核心
   - 编辑器能力封装

这条路线的核心判断是：

- 桌面端和移动端的交互模型差异很大，不能靠“一个前端强行多端复用”解决
- 当前最适合复用的是“业务能力”和“渲染逻辑”，不是整页 UI
- 如果直接硬复用 `web/admin`，桌面端会继承大量不需要的后台逻辑，包体、复杂度和维护成本都会明显变高

## 3. 推荐架构

### 3.1 总体结构

建议将前端扩展为如下结构：

```text
web/
├── admin/                    # 现有管理后台
├── app/                      # 现有用户端 Web
├── desktop/                  # 新增桌面端 Electron 应用
├── mobile/                   # 新增 Taro 应用（小程序 + H5）
└── packages/
    ├── icons/
    ├── themes/
    ├── ui/
    ├── api-client/           # 新增，统一请求封装
    ├── doc-core/             # 新增，文档渲染/解析/模型
    ├── chat-core/            # 新增，问答相关业务封装
    └── editor-core/          # 新增，编辑器能力封装
```

### 3.2 终端职责划分

| 模块 | 主要职责 | 是否建议复用现有页面 |
|------|----------|----------------------|
| `web/admin` | 后台管理、配置、发布、复杂编辑 | 保持现状 |
| `web/app` | 浏览、搜索、问答、公开访问 | 保持现状 |
| `web/desktop` | 本地/远程文档编辑、问答 | 不复用页面，只复用能力层 |
| `web/mobile` | 移动端文档查阅、问答 | 不复用页面，只复用能力层 |

## 4. 各端技术方案

## 4.1 桌面端方案

### 4.1.1 技术选型

推荐：

- **Electron**：桌面容器
- **React + Vite**：渲染层
- **Tiptap**：富文本编辑
- **Markdown 编辑器**
  推荐两阶段：
  - 第一阶段：继续使用现有 Markdown 解析/预览体系，自建编辑区
  - 第二阶段：根据体验再决定是否接入 CodeMirror 6
- **本地文件能力**
  - Electron 主进程负责文件读写、最近文件、导出
  - 渲染进程不直接碰 Node API

不推荐当前就上 Tauri，原因是：

- PandaWiki 现有前端是 React 生态，Electron 接入成本更低
- 桌面端的富文本编辑、文件关联、自动更新、剪贴板、拖拽、导出等能力，Electron 方案更成熟
- 团队后续如果还要补插件、系统菜单、托盘、全局快捷键，Electron 更稳

### 4.1.2 桌面端能力边界

桌面端建议只做四块：

1. 文档打开与管理
2. 富文本编辑/查看
3. Markdown 编辑/预览
4. AI 问答

明确不纳入第一阶段的能力：

- 知识库管理后台
- 成员/权限管理
- 发布流程
- 统计和运营配置
- 多人协同编辑
- 大文档分块协同

### 4.1.3 桌面端使用模式

桌面端建议支持两种模式：

#### 模式 A：本地模式

目标：替代 Typora。

能力：

- 打开本地 `.md`
- 新建/保存 Markdown
- 本地 Markdown 预览
- 打开 PandaWiki 导出的富文本内容或受支持格式
- 本地问答（可选，后续依赖远程接口）

#### 模式 B：远程知识库模式

目标：连接 PandaWiki 服务器。

能力：

- 登录 PandaWiki
- 浏览知识库文档
- 编辑富文本/Markdown 文档
- 提交保存到服务器
- 基于服务器内容进行问答

建议优先级：

- **先做远程模式**
  因为它能直接复用当前后端能力，业务闭环更快。
- **本地模式作为增强项**
  逐步补“最近文件、导出、自动保存、离线缓存”等桌面体验。

### 4.1.4 桌面端目录建议

```text
web/desktop/
├── electron/
│   ├── main.ts             # 主进程
│   ├── preload.ts          # 安全桥接
│   └── ipc/                # 文件、窗口、菜单等 IPC
├── src/
│   ├── pages/
│   │   ├── editor/
│   │   ├── markdown/
│   │   ├── chat/
│   │   └── login/
│   ├── components/
│   ├── hooks/
│   ├── store/
│   └── types/
├── package.json
└── vite.config.ts
```

### 4.1.5 桌面端与现有代码的复用策略

优先复用：

- `web/app` 的文档只读渲染能力
- `web/admin` 的编辑器能力和接口模型
- `web/packages/icons`
- `web/packages/themes`
- 未来抽出的 `api-client`、`doc-core`、`chat-core`、`editor-core`

避免直接复用：

- `web/admin` 的整页布局
- `web/admin` 的路由结构
- `web/admin` 中后台专属的状态、权限、设置页代码

原因很明确：

- 桌面端和后台不是同一个产品
- 直接复用页面，后期清理无关能力的成本会更高

## 4.2 App / 小程序方案

### 4.2.1 技术选型

推荐：

- **Taro + React**

输出目标：

- 微信小程序
- H5 移动站

原因：

- 一套 React 语法，可同时覆盖小程序和 H5
- 对“文档查阅 + 问答”这类轻交互场景足够
- 相比 React Native，同时兼顾小程序的投入更低

不推荐第一阶段直接做 React Native，原因是：

- 你当前最明确的诉求里，小程序是必须项
- RN 无法直接产出小程序
- 先做 RN 再做小程序，会形成两套移动端工程

### 4.2.2 移动端能力范围

只保留下面这些能力：

1. 登录 / 鉴权
2. 知识库列表
3. 文档目录浏览
4. 文档详情查看
5. 搜索
6. 问答
7. 历史会话

明确不做：

- 富文本编辑
- Markdown 编辑
- 文档结构管理
- 协同编辑
- 系统设置

### 4.2.3 移动端页面建议

```text
mobile/
├── 首页
├── 知识库列表
├── 文档目录页
├── 文档详情页
├── 搜索页
├── 问答页
└── 我的/登录页
```

### 4.2.4 移动端复用策略

优先复用：

- `web/app` 的接口协议
- `web/app` 的问答请求流程
- `web/app` 的 Markdown 渲染规则
- 共用 `api-client` / `doc-core` / `chat-core`

不建议复用：

- `web/app` 的 Next.js 页面层
- 依赖 DOM 的复杂渲染逻辑
- 依赖浏览器能力较重的组件

## 5. 共享层拆分设计

为了避免未来三四套前端各自复制粘贴，建议先把共享能力抽出来。

## 5.1 `packages/api-client`

职责：

- 统一请求封装
- Token 注入
- 错误处理
- 终端差异适配（浏览器 / Electron / Taro）

建议内容：

- 登录、用户信息
- 知识库与节点查询
- 文档详情
- 问答接口
- 上传下载基础能力

说明：

- 现有 `web/admin/src/request` 和 `web/app` 的请求层可以逐步向这里收敛
- 不建议一次性整体迁移，应该按模块逐步抽离

## 5.2 `packages/doc-core`

职责：

- 文档数据模型
- Markdown 渲染配置
- 文档树结构转换
- 文档内容格式判断
- 文档展示侧通用逻辑

建议包含：

- Markdown 渲染器配置
- Mermaid / KaTeX / 代码高亮规则
- 文档目录数据转换
- 内容摘要与元信息处理

## 5.3 `packages/chat-core`

职责：

- 问答请求流程
- 会话管理
- SSE / 流式输出处理
- 历史会话模型

原因：

- 问答是 Web、桌面端、App、小程序都需要的共性能力
- 这部分很适合做成终端无关的业务层

## 5.4 `packages/editor-core`

职责：

- 富文本编辑器的基础扩展集合
- Markdown 编辑器配置
- 编辑器工具栏能力定义
- 内容格式转换

注意：

- 这里只抽“能力”，不抽整页 UI
- 协同编辑逻辑不建议在第一阶段继续向多端推广
- 桌面端第一阶段默认只做单人编辑

---

## 6. 与现有 PandaWiki 的集成方式

## 6.1 后端接口层

当前后端大概率不需要为多端做大规模重构，只需要补几类能力：

1. 更稳定的终端鉴权方式
2. 更明确的文档读取/保存接口约束
3. 面向桌面端的“最近打开 / 草稿 / 导出”能力接口（如需要云同步）
4. 面向移动端的轻量化数据接口

建议原则：

- **能复用现有接口就复用**
- **只有当终端能力明显不同，再新增接口**

## 6.2 鉴权策略

建议：

- Web 继续保留现有方案
- 桌面端、App、小程序统一走 Token 鉴权
- 为多端补充：
  - 登录设备标识
  - 刷新 Token
  - 设备下线

这样后续做“登录设备管理”也更自然。

## 7. 分阶段实施路线

## 阶段 1：共享层整理

目标：先抽出未来多端都能复用的业务能力。

建议内容：

1. 新建 `web/packages/api-client`
2. 新建 `web/packages/doc-core`
3. 新建 `web/packages/chat-core`
4. 梳理 `web/admin` 和 `web/app` 中可复用的编辑器/渲染逻辑

产出结果：

- Web 现有能力不变
- 为桌面端和移动端打基础

## 阶段 2：桌面端 MVP

目标：先做可用的“PandaWiki 桌面编辑器”。

最小可交付能力：

1. 登录 PandaWiki
2. 浏览文档
3. 富文本查看/编辑/保存
4. Markdown 查看/编辑/预览/保存
5. 问答

可以暂缓：

- 本地文件关联
- 导出 PDF
- 离线模式
- 多窗口
- 自动更新

## 阶段 3：移动端 MVP

目标：先上线一个可用的小程序/H5 轻客户端。

最小可交付能力：

1. 登录
2. 知识库浏览
3. 文档查看
4. 搜索
5. 问答

## 阶段 4：终端增强

桌面端增强方向：

- 最近文件
- 本地缓存
- 离线只读
- 导入导出
- 系统菜单 / 快捷键
- 剪贴板 / 拖拽图片

移动端增强方向：

- 收藏
- 最近阅读
- 语音问答
- 分享到微信

## 8. 工作量评估

以下为相对粗粒度评估，默认已有 1 名熟悉当前前后端结构的工程师主导。

| 模块 | 复杂度 | 预估工作量 |
|------|--------|-------------|
| 共享层抽取 | 中 | 1 到 2 周 |
| 桌面端 MVP | 中到高 | 2 到 4 周 |
| 移动端 MVP（Taro） | 中 | 2 到 3 周 |
| 桌面端增强 | 中 | 1 到 3 周 |
| 移动端增强 | 中 | 1 到 2 周 |

说明：

- 如果目标是“先出能用版本”，桌面端优先级应高于移动端
- 如果目标是“尽快覆盖更多终端”，则共享层抽取必须先做，否则后面维护成本会失控

## 9. 风险与规避建议

## 9.1 最大风险：页面级复用过度

风险：

- 直接把 `web/admin` 或 `web/app` 页面塞进新终端，短期快，长期维护成本高

规避：

- 只复用业务能力和组件，不复用整页结构

## 9.2 第二风险：桌面端一开始就追求“全功能”

风险：

- 需求边界失控，桌面端会变成另一个管理后台

规避：

- 把桌面端收敛为“Typora + PandaWiki 问答 + 远程文档编辑”

## 9.3 第三风险：移动端编辑诉求扩散

风险：

- 小程序和 App 一旦接入编辑，复杂度会明显提升

规避：

- 明确移动端只做阅读和问答

## 9.4 第四风险：协同编辑继续向多端扩散

风险：

- 现阶段协同编辑本身已经是复杂模块，多端同步推进只会放大问题

规避：

- 桌面端和移动端第一阶段默认不做协同
- 先把单人编辑链路做稳

---

## 10. 推荐落地顺序

最推荐的实施顺序如下：

1. 抽 `api-client`、`doc-core`、`chat-core`
2. 新建 `web/desktop`，做桌面端 MVP
3. 桌面端稳定后，再新建 `web/mobile`
4. 最后再考虑桌面端本地模式增强与移动端体验增强

原因：

- 桌面端与你当前的编辑器能力最接近，价值最高
- 移动端需求更轻，放后面不会影响主链路
- 先做共享层，后面每新增一个终端都会更快

---

## 11. 最终建议

如果只给一个明确建议，推荐方案是：

- **Web 端保持现状**
- **桌面端使用 Electron 单独开发，只做问答 + 富文本/Markdown 编辑查看**
- **移动端和小程序使用 Taro，共享阅读和问答能力**
- **先抽共享业务包，再开始做新终端**

这套方案的优点是：

- 技术风险最低
- 与当前仓库结构最兼容
- 代码复用率高
- 可以逐步推进，不需要一次性重构现有 Web

这套方案的缺点是：

- 前期需要投入一轮共享层整理
- 不会得到“一个页面跑所有端”的极致复用

但对 PandaWiki 当前阶段而言，这个取舍是合理的。因为真正需要复用的是能力，不是页面。
