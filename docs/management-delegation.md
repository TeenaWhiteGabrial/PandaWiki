# 管理权限：继承与局部委派

管理权限在栏目、文件夹层级合并：任一适用的上级或本级授权命中即可管理。本级新增或清空规则不撤销上级管理权。栏目管理员持续管理整个栏目，局部管理员只管理被委派的子树，其祖先仅作为路径显示，不获得父级配置权。

新增授权仅限现有管理员账号，可跨组织选择，不要求目标已管理父目录。新规则范围固定为当前及下级目录。操作者必须先有目标的管理权；修改父级授权必须到来源处操作并通过该处鉴权。

文档使用所属目录的管理员，不再新增文档级管理授权。查阅权限、用户端问答范围保持原有计算；管理端可查看有管理权的内容，超级管理员始终兜底。移动和删除仍校验目标及受影响内容的权限。

## 历史配置

不迁移或清空业务数据。历史部门、等级、仅当前目录、文档级管理授权兼容保留；新规则不扩大历史范围。文档历史授权可整体清空，不能新增或改写为另一批人员。

注意：这是管理模型变更。过去被子级规则排除的上级管理员，现在恢复对该子树的管理权；一级文件夹自己的规则不再覆盖栏目管理员。这是新规则的预期行为，应在生产发布前核对管理员名单。

## 界面

弹窗展示有效管理员、只读的上级继承及授权来源、本级新增。批量操作只替换本级规则，各节点的继承分别生效。管理标签按合并授权说明，不再提示所有层级同时满足。

## 验证与发布

在独立空测试库验证委派、父级不能被局部覆盖、越权编辑拒绝、普通用户拒绝、文档新增拒绝、撤销本级授权及查阅规则保留；测试事务回滚。不涉及数据库迁移或索引重建。

首次发布需要更新 API 和管理端，不能只更新其中一端。沿用 `deploy/server/deploy.sh upgrade backend` 与 `upgrade admin`（需要保持 Consumer 停止时保留已有标志），原 Compose 项目、卷、数据库和存储配置不变。部署前备份并核对实际挂载与业务数据；部署后刷新管理端，检查实际授权及文档树。本地自动化验证不代表生产或完整浏览器流程已经验收。
