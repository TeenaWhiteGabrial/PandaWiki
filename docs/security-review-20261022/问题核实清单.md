## 三、主机自查方法（只读，不执行漏洞载荷）

- **R1**：核对 redis-server 版本、镜像摘要/编译来源、对应维护分支补丁与默认 ACL。`ACL GETUSER default` 的密码哈希不要对外发送；只记录 nopass、命令权限和是否有密码。RESTORE 可调用不等于已经执行成功 RCE；需要二进制补丁核对或隔离副本复现。
- **R2**：读取 `INFO replication`、`CONFIG GET replica-read-only`，确认主/副角色及 EVAL/复制管理权限。不要为验证漏洞去改副本配置。
- **R3**：向测试方要独立公告、CVE、补丁提交及样本；核对是否只是 R1 已覆盖的同一根因。
- **R4**：读取 `MODULE LIST`；没有 RedisBloom 时不能将 TDigest 模块漏洞判成已命中。
- **R5**：读取 `CONFIG GET tls-port` 以及 TLS 相关配置；当前本地 tls-port=0。核查官方提交是否进入所用构建；不要用会崩溃的 PoC 检查在线数据。
- **R6**：无凭据 PING 和默认 ACL 足以确认本地认证缺失；无需读取业务数据、执行 KEYS * 或试写文件。
- **N1**：无凭据 CONNECT/PING 能否得到 PONG。本轮只建立连接，不订阅、发布、修改 JetStream。
- **N2**：无凭据 GET /varz 的状态；同时检查端口绑定和防火墙。不要把“仅 localhost 可达”与“局域网任意人可达”混为一谈。
- **S1**：在你实际需要核实的 Ubuntu 主机自行运行 `dpkg-query -W openssh-server openssh-client`，核对发行版补丁包及当前运行进程。报告中的 8.9p1-3ubuntu0.17 不能仅按 8.9p1 上游号判断。以下公告只支持对应 CVE，不代表所有 OpenSSH 问题都已修复。
- **S2**：先确认漏洞落在 sshd、ssh、ssh-agent、ssh-add、scp 或 sftp 的哪一个程序，再查实际使用场景及配置。不要把客户端 CVE 当成远程服务端默认漏洞。
- **S3**：取得实际协商算法与服务端允许配置，指出具体弱算法，不能只给“探测到算法列表”。
- **G1**：对正确 Nginx 实例读取 `nginx -v`、`nginx -V`、相关 `nginx -T` 配置。T 输出可能含凭据，只在本机检查对应指令，不整体外发。三项分别检查 HTTP/3、HTTP/2 上游+头配置、字符集指令，不以组件版本代替条件核实。
- **P1**：检查本机监听、用途和访问边界。无对应服务则本地不适用；端口开放本身与软件漏洞分开记录。
- **P2**：区分认证后返回协议/版本信息和未认证泄露；不尝试导出数据库。
- **P3**：只读查看响应头；隐藏指纹是加固措施，不应代替真实补丁。

## 五、额外发现：P7 的测试配置偏差（N01，非报告新增漏洞）

- 当前本地“权限验收-受限栏目-20261021”的 navs.permissions 实际为 `{"visible":"open","visitable":"open","answerable":"open"}`，没有部门、等级或人员限制。
- P7 及其父目录 01-栏目继承都是 inherit:true；匿名请求 P7 正文成功。
- 因此你第一轮 pt_dev_g1 对 P7 回答成功，有明确的本地配置原因，暂不能归因于问答权限过滤失效。
- 受限 P2 的匿名正文请求则返回 Permission Denied，说明至少这一受限样本的接口过滤生效。
- 下一步由你确认受限栏目的目标配置：测试软件组（含下级）+只选涉密，排除 pt_denied；保存后重新打开并看最终权限，再复测 P7。此次核查没有替你修改权限。
